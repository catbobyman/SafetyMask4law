# 法律文件脱敏 Agent：功能与技术方案

日期：2026-11-01。状态：本文保留完整产品方案；本地 TXT、DOCX、PDF 闭环已实现并完成样例实测，宿主接入尚未实现。当前实现范围及运行方式以 [README](../README.md) 为准。

依据：[PRD](../PRD.md)、[业务规则](../规则.md)、[官方资料核查](HaS模型官方资料核查.md)、[交互原型](../prototype/README.md)。本方案细化现有需求，不替代《规则.md》。

## 1. 方案结论

借鉴官方 HaS 的扫描、脱敏、映射、还原流程，以及模型与程序分工、按 token 分块的思路。以官方接口和行为为参考，围绕本项目重新实现。

首版以 Codex、Claude Code、WorkBuddy 原生插件交付，采用：

**对话发起 → 本地工作台选材料 → HaS 识别 → 原文定位与规则处理 → 候选确认 → 程序替换并记录映射 → 脱敏稿交接给宿主模型 → 对话继续分析 → 本地还原结果。**

原格式导出是确认之后的独立分支，用于把文件发给他人。

HaS 使用 NER 能力发现候选；程序直接编辑确认后的原文位置，并在编辑时记录映射。不让模型生成最终合同全文，也不通过两份全文的差异倒推映射。

Agent 分两层：宿主模型完成用户的分析任务，只读取脱敏稿；Mask 按固定步骤自动执行脱敏工作流，不引入让模型自行选择工具的规划循环。遇到规则不确定或不支持的文档结构时，给出具体待处理项。

## 2. 官方设计如何借鉴

| 官方做法 | 本项目采用方式 | 对应需求 |
| --- | --- | --- |
| scan / hide / restore 命令 | 保留“扫描—脱敏—还原”的用户概念，增加候选确认 | 让用户能查看具体处理对象 |
| 固定 NER 模板 | 保持官方训练模板，类别来自规则的 JSON 结构块 | 使用 HaS 已有识别能力 |
| 模型识别，工具管理流程 | 模型找候选；程序定位、应用规则、替换、保存 | 限定模型职责 |
| 长文本按 token 分块 | 保留段落和原文位置，给输出预留上下文空间 | 支持合同、诉讼材料 |
| 保存映射、增量复用 | 使用项目级实体身份和标签映射 | 同项目同实体代号一致 |
| 官方 Hide 内部再次识别并生成全文 | 直接使用已扫描、已确认的候选生成编辑操作 | 确认到导出之间不重复识别 |
| Pair 比较原文和生成文本提取映射 | 每次确定性替换时同时记录原值与标签 | 映射来源可追溯，不需要模型 Pair |
| 文本工具处理纯文本 | 增加 DOCX 和原生 PDF 的读取与原位置编辑 | 支持可编辑 Word 与原版式 PDF |

## 3. 首版用户功能

### 3.1 发起与首次使用

- 用户在宿主对话输入入口和需求，入口按 [6.3](#63-宿主接入) 区分。这句话不经过脱敏，直接发给宿主模型。
- 技能要求模型先调用 `mask_start`，不读取材料。工作台由本地服务在默认浏览器打开，打不开时用户可使用对话中的链接。
- 首次运行检查本地服务、llama.cpp 和 HaS 模型，缺失时由向导安装并校验 SHA-256。安装失败时显示具体原因，不进入识别。

### 3.2 项目与选材料

- 工作目录即项目。再次发起时自动沿用该目录的实体身份、映射和核对进度。
- 工作台预列当前工作目录的文档，由用户勾选；这一步只列文件名，未勾选的文件不读取。也可添加其他位置的 TXT、DOCX 或原生 PDF。
- 同一批可选择多份文件，顺序识别。用户可写补充说明，其中的真名在交接前一起脱敏。
- 显示已读取的文字范围；发现扫描页或当前读取器不支持的结构时，说明未处理部分，不显示“全文已完成”。

### 3.3 扫描与候选确认

- 自动使用规则定义的 22 类实体扫描，不要求用户每次手工勾选全部类别。
- 每份文件显示排队、识别中或已完成；完成一份即可核对一份。
- 候选按原文出现位置显示，提供类型、原文、所在段落或页码、处理决定和具体依据。
- 决定分为“脱敏、保留/拒绝、不确定”；不展示模型未提供的置信度。
- 用户可确认或拒绝候选，修正类别和选中范围；也可在原文中划选漏检内容补录。
- 全文搜索用于查漏：已标注和未标注的命中分别显示，未标注内容可逐处或全部补录。
- 原文预览与候选列表联动。修改一处决定只影响该位置；实体身份可以共享，但不能自动把一处的拒绝传播到全文。按实体或相同内容批量处理必须由用户明确触发。
- 工作台提供“实体与代号”视图，代号表只在本地显示。
- 尚有“不确定”或位置冲突时，标记为待处理，完成处理后才能交接或导出。

候选确认是复杂规则目前的明确处理方式。首版不预设 HaS 能执行三态裁决，也不默认加入第二个判断模型。

### 3.4 交接与继续分析

- 待确认清零后，用户在汇总页查看各类别数量、保留和补录数量、未处理内容，以及将交给模型的内容，确认后才交接。不要求逐份确认文件。
- 程序按确认结果生成统一代号，替换对应范围，写入脱敏 Markdown。汇总页可预览全文，有疑问可返回修改。
- 交接内容使用材料编号，不含原始文件名、原件和映射。
- 宿主支持回传时自动继续；否则工作台提示回到对话发送“继续”。交接前发送“继续”时，模型回复材料尚未交接及待确认数量。
- 交接后修改决定或新增材料，该文件回到未交接状态，需重新确认。
- 区分“扫描完成、待确认、已交接、部分处理、失败”。一次模型调用成功不能代表文件处理成功。

### 3.5 导出原格式

- 待确认清零后可随时导出，与交接相互独立。
- TXT 导出文本，DOCX 导出可编辑 Word，原生 PDF 导出保留原页面布局的 PDF。
- 导出前列出当前版本未处理的内容，例如批注；这些内容可能保留在文件里。原文件不覆盖。

### 3.6 结果还原

- 在工作台选择结果文件或粘贴含代号的文本，真名版只保存到本地，不回传对话。
- 代码精确替换映射中存在的代号；遇到属于本工具格式但映射缺失的代号，列出缺项，标记为部分还原。
- 首版还原对象是文本中的代号，不承诺恢复 PDF 的原始字节或经过任意修改的文档版式。

## 4. 规则处理的实际责任

程序不能仅凭“模型说它是公司”就执行替换，也不能只靠名称后缀宣称完成全部法律语义判断。

| 能明确执行的判断 | 处理方式 |
| --- | --- |
| 候选不在对应原文范围中、响应截断或结构错误 | 报告识别/对齐失败，不作为空结果 |
| 空值、占位线、字段名或明确角色称谓 | 拒绝当前候选 |
| 有明确证据的受保护内容或类别错误 | 保留/拒绝，并记录依据 |
| 具体值、类别与上下文符合已实现规则 | 可判定脱敏，纳入确认预览 |
| 公司、法院、政府或其他主体的上下文不足 | 标记不确定，交用户裁决 |
| 候选夹带角色、标题或条款 | 拒绝整个错误范围；仍允许另行提出正确范围 |
| 候选相交、跨块边界不清 | 不凭长短任意取舍，提交位置冲突供修正 |

规则处理只使用《规则.md》的含义，不另起一份独立业务政策。实现时将每条可自动执行的判断与对应规则条目关联；尚不能执行的语义例外显示为待确认。

“已完成扫描”只表示所有可处理文本经过了流程，不等于证明没有漏检。确认界面应同时允许查看完整原文和补充候选。

## 5. 模型与代码分工

| 操作 | 模型 | 代码 / 用户 |
| --- | --- | --- |
| 读取 DOCX、PDF | 不参与 | 代码提取文字并保留结构位置 |
| 拆分长文 | 不决定文件拆法 | 代码按段落和 token 预算拆分 |
| 发现候选 | HaS NER | 代码组织固定模板、解析完整响应 |
| 确定每次出现的位置 | 不采用生成的字符偏移 | 代码与原文对齐 |
| 业务规则判断 | 首版不调用 HaS 做任意规则问答 | 明确规则由代码执行，歧义交用户 |
| 同主体、不同名称的合并 | 不默认相信自动指代推断 | 有明确简称定义或用户确认后共享身份 |
| 替换与映射 | 不生成最终全文 | 代码根据确认的位置同时生成文本与映射 |
| 导出文件 | 不参与 | 代码操作文档结构并验证输出 |
| 同语种文本还原 | 不参与 | 代码按标签映射替换 |
| 用户的分析任务 | HaS 不参与 | 宿主模型读取脱敏稿完成 |

原件、候选和映射留在本机，只有脱敏 Markdown 和脱敏后的补充说明交给宿主模型。HaS 通过 Windows 原生 llama.cpp 的本地 HTTP 接口调用。

## 6. 技术结构

核心是一个 Python 本地服务，配本机浏览器工作台；三个宿主的插件都是调用它的薄适配层。后端建议 FastAPI；页面先使用 HTML/CSS/JavaScript 实现选材料、核对、交接、导出和还原。首版不增加独立前端构建体系。[FastAPI 文档](https://fastapi.tiangolo.com/)

服务只绑定 `127.0.0.1`，端口随机，页面地址带一次性令牌。工作台能读到原文和映射，而本机任何网页都能向 localhost 发请求，不加令牌就可能被读取。

按六个模块组织，模块内部承接实际复杂度，不为尚不存在的第二模型设计通用插件框架：

| 模块 | 对外接口的职责 | 内部实现 |
| --- | --- | --- |
| 文档模块 | 读取文档；按已确认编辑导出原格式和 Markdown | TXT、DOCX、PDF 三种格式适配，源位置、结构和输出验证 |
| 识别模块 | 输入文本与类别，返回候选 | 分块、token 预算、固定 NER 模板、本地 HTTP 调用及响应解析 |
| 规则模块 | 输入候选及所在上下文，返回三态决定和依据 | 已明确实现的规则、边界判断、不确定项 |
| 映射模块 | 为确认实体分配标签；保存和加载映射；还原文本 | 项目身份、不同写法、标签唯一对应关系 |
| 工作流模块 | 扫描、应用确认、交接、导出、还原 | 串联步骤、保存项目状态、向界面报告进度和失败 |
| 宿主接入模块 | 提供 `mask_start`、`mask_status`；各宿主的技能和 hook | 启动本地服务、打开工作台、按宿主差异返回或等待、输入拦截 |

DOCX 以 python-docx 为首选，必要时使用其底层 XML 定位当前文档中实际出现的结构，不通过整段重新赋值破坏所有 run 格式。[python-docx 文档](https://python-docx.readthedocs.io/en/latest/)

PDF 的技术候选为 PyMuPDF，用字符位置进行 redaction 和标签写入。是否最终采用，需通过原版式样例探针，并核对项目分发方式与依赖许可；它不能仅凭库名称就保证所有 PDF 都能原版式编辑。[PyMuPDF Page 接口](https://pymupdf.readthedocs.io/en/latest/page.html)

项目状态和映射使用本地 JSON，放在工作目录外的插件数据目录，按工作目录路径区分项目。宿主模型能读工作目录，映射放在里面就可能被读取。首版顺序处理和保存，不引入数据库、任务队列或并发写入机制。

### 6.1 必须保存的信息

- **项目**：工作目录路径、核对进度和交接状态。
- **文档**：原文件、格式、可处理文本及对应源位置。源位置由读取器生成，后续编辑使用同一份原文件快照。
- **候选出现**：文档、位置、原始字符串、类别、处理决定、依据。身份共享与位置决定分开保存。
- **实体身份**：项目内 ID、类别、已确认的名称或简称、使用的代号。
- **替换记录**：源位置、原值、标签。生成替换时写入，用于映射和输出核对。

确认后的原文件或规则发生变化时，已有结果标记失效，需要重新扫描受影响的文档；不能沿用旧偏移编辑新内容。

### 6.2 同一主体与精确还原

同一个公司可以有全称和简称。若两种写法使用完全相同的标签，则“标签→多个原值”的映射无法确定某次原来用了哪种写法。

使用共享主体编号、区分写法的标签：首个写法用 `⟦公司1⟧`，之后确认的其他写法依次用 `⟦公司1·2⟧`、`⟦公司1·3⟧`。它们都表示公司 1，但每个标签只对应一个原值。首个写法不加后缀，是因为标签可能已经交给模型，后来才发现简称时不能改动已交接的代号。罕见括号和编号形式在实现前统一固定。

这项设计服务于“同实体一致”和“文本可精确还原”，不依赖模型猜测应还原成全称还是简称。若原文已经含有本工具拟生成的标签，分配标签时避开冲突。

### 6.3 宿主接入

以下来自官方文档和本机安装目录，尚未在宿主中实际调用。

| 项目 | Claude Code | Codex | WorkBuddy |
| --- | --- | --- | --- |
| 入口 | `/mask`，重名时用带插件名的完整形式 | `$mask`；不提供自定义 `/` 命令 | `/mask`，依据是第三方教程，需实测 |
| 插件内容 | 技能、MCP、hook | 技能、MCP；hook 需手动安装并经用户信任后运行 | 技能、连接器（支持 stdio MCP）；本机插件样例含 hook |
| 回到对话 | MCP 调用超过 2 分钟转后台，完成后通知主对话 | 工具默认 60 秒超时，默认由用户发送“继续” | `mcp.json` 有 `timeout`，回传机制未见官方说明，默认由用户发送“继续” |
| 对话内自定义界面 | 文档未提及 MCP Apps | `enable_mcp_apps` 开发中，默认关闭 | 未见说明 |

因此采用以下做法：

- **工具接口：** `mask_start` 接收需求，启动服务并打开工作台。Claude Code 上它等待工作台完成后返回；Codex 和 WorkBuddy 上立即返回链接，结束本轮。`mask_status` 返回当前状态和已交接文件路径。
- **交接方式：** 脱敏 Markdown 写入工作区的 `mask-handoff/材料N.md`，工具只返回路径和清单。工具输出有 token 预算，全文放进返回值可能被截断；写成文件后，追问时模型也能重新读取。
- **界面：** 对话中只用文字、表格和链接，按钮和表单都放在工作台。
- **拦截：** 用 `UserPromptSubmit` hook 拦截 `@` 引用的文档和已确认的真名，并提示改用代号。它能阻止发送，不能改写内容。Codex 文档明确说工具 hook 不是完整的强制边界；Claude Code 文档未说明这个 hook 与 `@` 展开的先后顺序。

## 7. 文件导出的具体处理

### 交给 AI 的 Markdown

按读取器保留的标题、段落和表格结构输出，文本来自已确认替换后的结果，不含页面版式。批注、修订等未读取的内容不进入 Markdown。

### TXT

按原文偏移从后向前替换已确认范围，保留非目标字符和换行。替换范围必须互不冲突。

### DOCX

将段落文字映射到 run 和字符范围；实体跨 run 时，只改对应片段，保留周围字符格式。处理正文、表格及页眉页脚；读取时检查脚注、修订、文本框等内容是否存在，若现阶段无法正确处理，明确列出，不能将该文件标为完整完成。

### 原生 PDF

将文字匹配到页面字符位置，执行真正的目标文字移除后写入标签。不能用白块覆盖替代底层文字处理。导出后重新读取目标区域及附近文字，并渲染核对是否误删周围内容。

标签可能比原文长。原版式探针需要验证中文字体、罕见括号、换行与可容纳宽度；放不下时提供具体失败位置或让用户选择同规则下的更短代号，不越过邻文、不悄悄重排整页。

1. 阅读官方代码是为了核实数据流、输入输出和失败条件，提炼行为说明后按本项目接口重新实现。

3. NER 的固定提示词属于模型使用协议，应保留准确格式并标注来源；不能为追求表面差异而改坏协议。
4. 在项目文档保留官方模型、工具版本及所参考文件的链接，明确哪些是官方能力、哪些是本项目设计。
5. 经用户确认，当前复用官方 1.0.3 的 `run_scan` 和 `_tool_seek`，通过适配层调用，不修改官方文件；文档处理与核对流程自行实现。来源及许可见 [第三方组件](第三方组件.md)。

不承诺“优化”已经提升实测指标。当前可确认的是流程上的改变：候选确认后不再重复 NER、不生成最终全文、不再需要通过 Pair 倒推映射。

## 9. 实现顺序与必要验证

| 阶段 | 可运行结果 | 直接相关的验证 |
| --- | --- | --- |
| 1. 模型、文件与宿主探针 | HaS NER 返回真实候选；DOCX/PDF 各完成一个原位置替换样例；三个宿主各跑通一次入口和打开工作台 | 模型调用完整性；跨 run；PDF 底层移除、字体和标签宽度；回到对话和 hook 拦截的实际行为 |
| 2. 文本闭环 | 导入 TXT、规则决定、候选确认、交接、映射还原 | 22 类代表样例、保留内容、空字段、位置冲突、还原一致性 |
| 3. 项目与文档闭环 | 同项目多份文件顺序处理；DOCX/PDF 导出；项目续接 | 代号一致、简称写法、结构覆盖、原文件不覆盖 |
| 4. 三端接入 | 三个插件可安装；首次运行向导可用；从发起到还原全流程可用 | 交接内容只含脱敏稿、长时间核对后能回到对话 |
| 5. 首版验收 | 三个宿主按 PRD 跑通完整流程 | 漏检、误删、边界错误；文件可打开；非目标内容保留 |

阶段 2 是开发过程中的可运行子集，不能替代 PRD 对首版 TXT、DOCX 和原生 PDF 的完整要求。

本方案暂不纳入 OCR、图片/签章处理、跨语言还原、生成式全文 Hide、第二模型和批量并发。这些不属于当前首版已明确的实现范围。

## 10. 当前尚需通过样例回答的问题

- HaS 对本项目 22 类候选的召回和边界准确性，尤其是案号、内部编号、支行、律所及简称。
- 程序规则能自动裁决多少候选；其余候选需要用户确认的比例。
- PDF 字符定位、罕见括号字体和长标签在真实页面中的表现。
- 哪些 DOCX/PDF 结构可以可靠处理，哪些需要明确报告未处理。
- Claude Code 长时间核对是否受 stdio 30 分钟空闲窗口影响。
- Codex 的工具超时能否由插件设置，`codex queue` 能否实现自动续接。
- WorkBuddy 的 `/mask` 调用、回传方式，以及本机插件目录的格式是否适用于用户安装的插件。
- 各宿主沙箱是否允许启动本地服务和打开浏览器。
- `UserPromptSubmit` 是否先于 `@` 展开运行。
- 三个宿主的 Python 运行环境、llama.cpp 的获取方式和分发许可。

这些结果决定首版能自动做到什么程度，不影响先采用上述职责分工。方案阶段没有进行安装、模型下载或功能实现。
